## Запуск

Python 3.11+ и зависимости из `requirements.txt` (проверено на pandas 3.0.1 и NumPy 2.3.5). Из папки проекта:

```powershell
python -m pip install -r requirements.txt
python -m unittest discover -s . -v
python pipeline.py --input-dir data/raw --output-dir data/processed
```

Можно указать любую папку с тремя исходными файлами с исходными именами. Повторный запуск перезаписывает одноимённые результаты. Исходные CSV не изменяются. Разделитель CSV — `;`, кодировка результатов — UTF-8 с BOM.

## D-01: проверки и соединения

- Идентификаторы читаются строками; крайние пробелы в ID удаляются, пустые ID считаются пропуском.
- Полностью одинаковые анкеты сворачиваются. Если одному ID соответствуют разные анкеты, все его анкеты откладываются. Первая запись произвольно не выбирается.
- Платежи с конфликтным ID не входят в основной граф. Это консервативное правило до уточнения источника, а не исправление ID.
- Профили присоединяются с проверкой `one_to_one`, чтобы соединение не размножало суммы.
- Множество вершин — объединение ID из анкет, платежей и F–U. Непрофилированные контрагенты и изолированные компании сохраняются.
- Связи F–U сохраняются отдельно. `F_LINK_COUNT` означает только число различных связанных F; семантика владельца или сотрудника не предполагается.
- Контроль: входящие и исходящие суммы и количества совпадают с итогами рёбер и CSR; каждая исходная строка платежей попадает либо в граф, либо в карантин.
- Распределения считаются по однозначным анкетам, а исходные пропуски и числовая статистика — по всей выгрузке. Поэтому их знаменатели могут различаться.

## D-03: политика платежного графа

Ребро направлено **от PAYER к BENEFICIARY**. Каждая строка источника интерпретируется как агрегат по направленной паре. Сумма и количество — разные веса.

В карантин попадают:

1. Строки без отправителя или получателя.
2. Нечисловые, бесконечные, отсутствующие и неположительные суммы.
3. Отсутствующие, нецелые, неположительные или выходящие за int64 количества.
4. Платежи с неоднозначной анкетой участника.
5. Самоплатежи (`PAYER == BENEFICIARY`).
6. Все строки повторяющейся направленной пары. Без периода и ID операции нельзя отличить дополнительные агрегаты от дублей, поэтому они не складываются автоматически.

Флаги причин могут пересекаться. Их сумму нельзя принимать за число исключённых строк. Самоплатежи доступны в карантине по флагу `self_payment`; они не входят в показатели межфирменных платежей.

### Признаки компании

- `IN_DEGREE` / `OUT_DEGREE`: число различных отправителей / получателей.
- `IN_AMOUNT` / `OUT_AMOUNT`: сумма поступлений / выплат в единицах источника.
- `IN_COUNT` / `OUT_COUNT`: число входящих / исходящих платежей.
- `IN_AVG_PAYMENT` / `OUT_AVG_PAYMENT`: общая сумма, делённая на общее количество, а не среднее средних по контрагентам.
- `IN_TOP1_SHARE` / `OUT_TOP1_SHARE`: доля самого крупного контрагента в сумме соответствующего направления.
- `RECIPROCAL_NEIGHBORS`: число контрагентов, с которыми платежи есть в обе стороны.
- `WEAK_COMPONENT`, `WEAK_COMPONENT_SIZE`: связная компонента при игнорировании направления и её размер; номера компонент имеют смысл только внутри этого запуска.

Суммы, количества и степени равны нулю, если в очищенном графе рёбер нет. Средние и доли в этом случае отсутствуют. Ноль означает отсутствие наблюдений в очищенной выборке, а не отсутствие бизнеса.

Используйте флаги `HAS_PROFILE_RECORD`, `HAS_USABLE_PROFILE`, `PROFILE_CONFLICT`, `HAS_RAW_PAYMENTS`, `HAS_CLEAN_PAYMENTS`, `HAS_EXCLUDED_PAYMENTS`, чтобы отличать покрытие от качества данных. Наличие исключённых строк означает, что показатели компании могут быть неполными.

## D-04: ОКВЭД

Уточнено по доске Miro: **раздел → класс → группа**. Например, `01.11.1 → A / 01 / 01.11`, `46.34.2 → G / 46 / 46.34`. `OKVED_L1/L2/L3` теперь соответствуют разделу/классу/группе; также добавлены явно названные `OKVED_SECTION/CLASS/GROUP`. Это заменяет прежнюю временную схему с подклассом.

Исходный `MAINOKVED_CODE` сохраняется. Ведущие нули не теряются. Из короткого кода более подробные уровни не выдумываются. `OKVED_FORMAT_VALID` проверяет только структуру строки, а не существование кода в официальном справочнике. Неверный формат даёт пустые производные уровни, но компания остаётся в данных. Родительские названия не генерируются.

Соответствие разделов и классов сверено с [таблицей на сайте ФНС](https://www.nalog.gov.ru/html/sites/www.rn27.nalog.ru/Documents/2018/OKVED.pdf). Это структурная таблица, а не полный справочник действующих детальных кодов; соответствие редакции классификатора исходной выгрузке ещё требует подтверждения. `OKVED_SECTION_KNOWN` отдельно показывает, найден ли класс в таблице.

## Открытые вопросы к организаторам

- Период, валюта и масштаб `PAY_AMT`, правила расчёта `PAY_CNT`.
- Статусы операций, возвраты, технические переводы и состав самоплатежей.
- Почему ID `U_428697` связан с разными анкетами; является ли это коллизией обезличивания.
- Охват банков/счетов: отсутствие ребра не равно отсутствию реальной связи.
- Семантика F–U и категорий полей, особенно `NEGATIVEMARK`.
- Версия полного справочника ОКВЭД для исходной выгрузки.

Без дат нельзя строить динамику, давность, регулярность и временное затухание весов. Без назначения операции нельзя подтвердить, что связь — поставка товара или услуги. Денежные веса не называются рублями и не сравниваются с годовой выручкой до согласования периода и единиц.
