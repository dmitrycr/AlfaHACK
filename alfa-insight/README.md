# Alfa Insight

Бэкенд персонализированной новостной аналитики. Эта итерация реализует вход,
профили компаний, сбор публикаций из локальных мок-источников, кандидаты событий
и наблюдаемость. Реальные СМИ, LLM, фронтенд и обучение моделей не подключены.

## Запуск

Требуются Docker Desktop / Docker Engine с Compose v2 и Python 3.
Для разработки вне контейнеров нужен Go 1.25.1.

Из каталога `alfa-insight`:

```sh
make setup
make up
make collect
make e2e
```

`setup` создаёт локальный `.env` с независимыми случайными секретами и правами
`0600`. Существующий `.env` сохраняется. `make up` собирает и поднимает пять
сервисов, PostgreSQL и Kafka, применяет миграции и загружает синтетические данные.
Планировщик также собирает мок-источники автоматически.

- API: <http://localhost:8080/api/v1/auth/me>.
- OpenAPI: <http://localhost:8080/openapi.json>.
- Работоспособность: <http://localhost:8080/healthz>.
- Готовность БД шлюза: <http://localhost:8080/readyz>.
- Логи: `make logs`.
- Остановка с сохранением данных: `make down`.

Файлы Compose staging/production остаются заготовками. Текущий Compose предназначен
для локальной разработки: один Kafka-брокер, внутренняя сеть, порты опубликованы
только на loopback. PostgreSQL и Kafka доступны с хоста на `15432` и `19092`.
Графического интерфейса в этом изменении нет.

## Тестовые учётные записи

Пароль из `.env`: по умолчанию **`DemoOnly-2026!`**. Эти учётки синтетические.

| Email | Компания |
| --- | --- |
| `metal@example.test` | `company-metal` |
| `metal2@example.test` | `company-metal` |
| `build@example.test` | `company-build` |
| `import@example.test` | `company-import` |
| `agro@example.test` | `company-agro` |

Бизнес-ролей нет. Пользователь получает доступ к своей компании. Публичные
мок-публикации общие; ручные загрузки, их задания и события приватны для компании.
В production запрещены `SEED_DEMO=true` и небезопасные сессионные cookie.

Пример входа и получения профиля:

```sh
curl -c /tmp/alfa-cookies -H 'Content-Type: application/json' \
  -d '{"email":"metal@example.test","password":"DemoOnly-2026!"}' \
  http://localhost:8080/api/v1/auth/login
curl -b /tmp/alfa-cookies http://localhost:8080/api/v1/companies/current/profile
```

Для POST после входа нужен `X-CSRF-Token` из ответа входа или `/auth/me`.
Для ручной загрузки дополнительно требуется `Idempotency-Key` длиной 8–128 символов.

## Компоненты

| Сервис | Текущая реализация | Схема PostgreSQL |
| --- | --- | --- |
| `api-gateway` | REST, сессии, CSRF, ограничение входа, внутренний контекст доступа | `auth` |
| `company-service` | Компании, версии профиля, происхождение каналов | `company` |
| `news-service` | Мок-источники, парсеры, очередь, версии публикаций, outbox | `news` |
| `event-service` | Кандидаты событий, источники, версии, интерфейс тегирования | `events` |
| `analytics-service` | Идемпотентные счётчики обработки и задержки доставки | `analytics` |
| `knowledge-service` | Зарезервирован; контракт будущего контекста описан в документации | — |
| `ranking-service` | Зарезервирован; JSON-контракт Match | — |
| `forecast-service` | Зарезервирован до согласования прогнозного сценария | — |
| `ai-agent-service` | Зарезервирован; JSON-контракты Trace и Insight | — |
| `insight-service` | Зарезервирован; JSON-контракт Insight | — |

Каждый рабочий сервис имеет отдельный Go-модуль и роль PostgreSQL. Сервисов
хранения-посредников нет. Чужие таблицы напрямую недоступны; синхронное общение
идёт через gRPC, уведомления — через Kafka. `libs/go` содержит общие технические
средства и модели контрактов, а не общую бизнес-логику.

## Импорт подготовленных компаний и профилей

Импортёр принимает нормализованный CSV и JSON-массив профилей. Примеры находятся в
`services/company-service/internal/service/testdata/`. Он проверяет типы и ОКВЭД,
сохраняет неизвестные флаги как null и не рассчитывает ML-признаки.

```sh
cd services/company-service
go run ./cmd/app import --dry-run \
  --companies internal/service/testdata/companies.csv \
  --profiles internal/service/testdata/profiles.json
```

Dry-run не подключается к БД. Для записи запускайте ту же команду без `--dry-run`
с DATABASE_URL роли company-service. Весь пакет записывается атомарно; одинаковый
повтор безопасен, изменение требует следующую версию профиля. Максимум пакета —
10 000 компаний / 10 MiB входа. Реальные файлы кейса требуют отдельного маппинга.

## Сбор новостей

По умолчанию активны шесть локальных источников: полный RSS, RSS с анонсом,
Atom, HTML со списком, HTML с JSON-LD и JSON API.

Конфигурация и ответы находятся в
`services/news-service/internal/source/fixtures/`. Источники имеют домены `.test`.
Неизвестный мок-адрес отклоняется. Переключение `SOURCE_MODE` на HTTP намеренно
запрещено; HTTP-загрузчик пока используется только в тестах.

После чистого сбора ожидаются:

- Семь валидных публичных публикаций.
- Шесть групп точных дублей и шесть кандидатов событий.
- Одна изолированная запись без даты публикации.
- У кандидатов состояние `awaiting_tagging`; реальный ML не вызывается.

Повторный сбор не создаёт новые публикации, версии или сообщения обработки.
`sources-updated.json` моделирует изменение одной статьи с 14% на 16%; сквозной
тест проверяет сохранение новой версии и обновление ссылки в событии.

Публикации разных источников сохраняют своё происхождение даже при одинаковом
тексте. Смысловое объединение и выделение нескольких событий — будущая задача ML.
Связь событие ↔ публикация в БД допускает несколько записей в обе стороны.

## Проверки

```sh
make test       # Модульные тесты; PostgreSQL-тесты без DSN явно пропускаются
make vet        # Статические проверки
make race       # Тесты с детектором гонок
```

Интеграционные тесты создают отдельную БД на каждый тест и удаляют только её:

```sh
export TEST_DATABASE_URL='postgres://test_admin:password@127.0.0.1:5432/postgres?sslmode=disable'
make integration
make race
```

Администратор должен иметь право создавать/удалять тестовые БД. Используйте
отдельный локальный тестовый PostgreSQL. Существующие БД тесты не очищают.

Если Docker недоступен, можно проверить пять настоящих процессов на PostgreSQL и
мок-брокере Kafka из `franz-go`:

```sh
make native-e2e
```

Для этого дополнительно нужны `psql` в PATH и `TEST_DATABASE_URL` локального
тестового администратора. Скрипт создаёт отдельную БД и пять независимых ролей,
проверяет запрет доступа к чужой схеме, запускает реальные бинарники и убирает
свои процессы, БД и роли после завершения. Это проверка Kafka-протокола на моках;
настоящий Apache Kafka проверяется Docker-сценарием в CI.

Проверка контрактов:

```sh
python3 -m venv .venv
.venv/bin/pip install -r scripts/requirements-contracts.txt
.venv/bin/python scripts/check-contracts.py
```

CI находится в **корне Git-репозитория**: `../.github/workflows/backend-ci.yml`.
Он проверяет Go-код с PostgreSQL и отдельно запускает Docker E2E с Apache Kafka.

## Переменные окружения

Перечень для Compose — в `.env.example`. Внутри сервисов используются:

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Подключение своей роли к PostgreSQL |
| `INTERNAL_KEY` | Секрет внутреннего подписанного контекста, минимум 32 байта |
| `KAFKA_BROKERS` | Список брокеров через запятую |
| `HTTP_ADDR`, `GRPC_ADDR` | Адреса слушателей |
| `APP_ENV` | Окружение; production запрещает демо-seed |
| `SEED_DEMO` | Загрузка синтетических компаний и учёток |
| `DEMO_PASSWORD` | Пароль синтетических учёток при первом создании |
| `APP_ORIGIN` | Единственный разрешённый браузерный Origin |
| `COOKIE_SECURE` | Secure-cookie; обязателен в production |
| `SOURCE_MODE` | В этой итерации только `fixture` |
| `SOURCE_CONFIG` | Необязательный путь к локальному JSON-конфигу источников |
| `RUN_SCHEDULER` | Отключение фонового сбора для контролируемых тестов |
| `COMPANY_ADDR`, `NEWS_ADDR`, `EVENTS_ADDR`, `ANALYTICS_ADDR` | gRPC-адреса соседей шлюза |

Пароли, созданные при инициализации PostgreSQL, сохраняются в его volume.
Редактирование `.env` само по себе их не меняет. Скрипты не удаляют volume и не
сбрасывают существующие учётки.

## Безопасность и ограничения

Сессионный идентификатор хранится в HttpOnly-cookie; в БД лежит его хеш.
Есть абсолютный срок 8 часов, idle-timeout 30 минут и отзыв при выходе.
Данные компании определяются по сессии. Внутренние gRPC-запросы подписываются с
аудиторией и коротким сроком жизни; обычные пользовательские заголовки не дают прав.
В локальном окружении сервисы доверенные и используют общий HMAC-секрет. Перед
производственным развёртыванием нужны раздельные сервисные ключи/идентичности и TLS.

Raw-ответы ограничены 2 MiB и удаляются через семь дней. Версии текста сохраняются
для восстановления оснований обработки. Запросы к внешним сайтам не выполняются.
LLM-вызовов и потраченных токенов в этой итерации нет; качество ML не измерялось.

Реальные CSV/XLSX, аналитика банка и фронтенд не изменены и в мок-набор не включены.
Импорт реальных файлов требует проверки колонок и согласования с ML-контрактом.
Пока нет персонализированного скоринга, готовых инсайтов, чата или прогнозов.
