# LLM API для фронта

Все пути начинаются с `/api/v1`. Компания берётся из сессии: `company_id`, промпт,
модель, профиль и оценка релевантности от фронта не принимаются. Бизнес-ролей нет.
Запросы используют существующую cookie-сессию (`credentials: "include"`).
На POST нужны `Content-Type: application/json`, `X-CSRF-Token` и
`Idempotency-Key` длиной 8–128 символов из `[A-Za-z0-9_.:-]`.

## Создание карточки

1. `GET /events/prepared?limit=20&offset=0` — события после разбора LLM.
   Ответ: `{items: Prepared[], limit, offset}`. ML-совместимые поля находятся в
   `items[].event`, версии и служебные признаки — рядом, вне этого объекта.
2. `POST /insights` с телом `{"event_id":"<event_id>"}` → HTTP 202, объект задания.
3. `GET /insights/<id>` — опрашивать с интервалом 1–2 секунды до конечного статуса.
4. `GET /insights?limit=20&offset=0` — задания и карточки текущей компании.

Повтор POST с тем же ключом и событием возвращает прежнее задание даже после
обновления профиля. Для новой карточки по обновлённым данным нужен новый ключ.
Карточки доступны сотрудникам своей компании.

```json
{
  "id": "<job_id>",
  "kind": "insight",
  "company_id": "<company_from_session>",
  "status": "pending",
  "attempts": 0,
  "result": null,
  "error_code": "",
  "created_at": "2026-10-23T10:00:00Z",
  "updated_at": "2026-10-23T10:00:00Z"
}
```

Статусы: `pending`, `running`, `retry`, `ready`, `failed`, `obsolete`, `uncertain`.
В `ready` поле `result` содержит карточку; `failed` означает исчерпание попыток;
`obsolete` — изменение входной версии. `ready`, `failed`, `obsolete`, `uncertain` — конечные.
`uncertain` означает, что провайдер мог выполнить запрос. Не отправляйте
повтор с новым ключом автоматически; требуется сверка результата оператором.
Не показывать ошибку задания как пустую успешную карточку.

Карточка содержит `card.summary`, шесть блоков `card.blocks`, утверждения
`card.statements` со слоями `fact`, `bank`, `ai`, ограничения `card.limitations`.
У утверждений `profile_features` — ID признаков, а `sources` — URL. Их подписи
и метаданные находятся в `result.profile_features` и `result.sources` — это
снимок оснований карточки, который сохраняется после обновления профиля.
`confidence` — уровень уверенности результата, не вероятность и не скор ML.
`event_version` и `profile_version` фиксируют использованные версии; карточка
не переписывается автоматически после обновления новости.

`synthetic: true` требует видимой отметки «Демонстрационные данные». Мок-провайдер
не даёт содержательных инвестиционных выводов. Синтетические материалы банка
также помечены в контексте и названии источника.

## Чат по карточке

1. `POST /chat/threads` с `{"insight_id":"<ready_insight_id>"}` → HTTP 202,
   `{id, company_id, insight_id, created_at, messages: []}`.
2. `POST /chat/threads/<thread_id>/messages` с `{"message":"Что произошло?"}`
   и новым `Idempotency-Key` → HTTP 202, задание сообщения.
3. `GET /chat/messages/<job_id>` — ожидать `ready`, `failed` или `obsolete`.
   Результат: `{thread_id, question, answer, run_id, synthetic}`.
4. `GET /chat/threads/<thread_id>?limit=20&offset=0` — история заданий в порядке
   создания. История доступна только создателю диалога в его компании.

`answer` содержит `text`, `sources`, `insufficient_data`, `limitations`.
При `insufficient_data: true` ответ явно сообщает, что сведений недостаточно.
Один диалог обрабатывает одно сообщение за раз. Новый вопрос во время обработки
предыдущего возвращает 503 `processing_in_progress`; повтор того же запроса
с прежним ключом возвращает прежнее задание. Тот же ключ с другим текстом — 409.
Контекст чата закреплён за версиями карточки. В модель передаются последние
шесть завершённых пар сообщений; вся история остаётся в БД.

## Ошибки и диагностика

Общий формат: `{"code":"...","request_id":"..."}`.

| HTTP | Значение |
|---|---|
| 400 | Некорректное тело, неизвестное поле, неверный ключ |
| 401 / 403 | Сессия, CSRF или доступ |
| 404 | Объект отсутствует либо принадлежит другой компании/пользователю |
| 409 | Ключ идемпотентности уже использован с другим запросом |
| 422 | Нужный результат/снимок ещё не готов или версия изменилась |
| 429 | Исчерпан лимит прямой операции LLM |
| 503 / 504 | Занятый диалог, недоступность зависимости или таймаут |

Если исходное событие ещё не подготовлено, создание карточки сейчас возвращает
404; в режиме `MATCH_MODE=external` отсутствие актуального Match — 422.
Ошибки фоновой LLM-операции отражаются в задании, а не HTTP-ошибкой GET.
После трёх неудачных попыток разбора новость переходит в `tagging_failed`;
`noise` и `insufficient_data` не попадают в `/events/prepared`.

`GET /ai/runs/<run_id>` возвращает технический журнал без промпта, секретов и
текста диалога. В карточке есть `run_id` и `check_run_id`. Токены и стоимость
в текущем режиме симуляционные; `cost_minor` выражен в копейках.

Полные проверяемые JSON-примеры: [examples/llm](examples/llm).
Схемы: `/openapi.json`, `contracts/events/llm.schema.json`.


## Оркестратор v2

Карточка выполняется через агента профиля, агента интерпретации и агента проверки.
`result.business_profile` содержит наблюдения и отдельно гипотезы с ID признаков;
это интерпретация, а не замена фактов Company/Profile. В результате также есть
`workflow_id` и `profile_run_id`. `GET /ai/workflows/<workflow_id>` показывает
статусы шагов, модели и run ID. Область доступа совпадает с областью сценария.

В ответе чата также есть `workflow_id`. Ключ и настройки провайдера фронт не
передаёт. По умолчанию всё остаётся моковым; HTTP-адаптер реализован, но платные
вызовы заблокированы до подтверждения контракта и тарифной единицы.

Журнал теперь содержит `cost_nano_rub`, `reserved_nano_rub`, `reasoning_tokens`,
`cost_estimated`. Нанорубли — основной точный учёт; `cost_minor` округлён вверх.
`cost_estimated=true` нельзя показывать как подтверждённое списание.
