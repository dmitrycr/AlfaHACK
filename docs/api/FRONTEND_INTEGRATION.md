# Alfa Insight — инструкция по подключению фронтенда

Версия API: 0.2.0. Актуально на 22 октября 2026 года.

Документ описывает реализованный API: регистрацию сотрудника, проверку компании,
вход, сессии и получение данных. Проверка компании, доставка писем и источники
новостей сейчас работают на моках. Интерфейс фронтенда реализуется отдельно.

## 1. Адреса и общие правила

| Параметр | Значение для локальной разработки |
| --- | --- |
| Backend | `http://localhost:8080` |
| Базовый адрес API | `http://localhost:8080/api/v1` |
| Полный контракт OpenAPI | `http://localhost:8080/openapi.json` |
| Пример адреса фронта | `http://localhost:3000` |

Все пути ниже указаны относительно базового адреса API. Например, `/auth/login`
означает `http://localhost:8080/api/v1/auth/login`. Если backend находится на другом
компьютере, адрес предоставляет бэкендер; `localhost` относится к текущему компьютеру.

Правила запросов:

- JSON в UTF-8, названия полей — `snake_case`.
- POST с телом: `Content-Type: application/json`.
- Для всех запросов браузера: `credentials: "include"`.
- ИНН и идентификаторы передаются строками.
- Даты передаются в ISO 8601 с часовым поясом, например `2026-10-22T17:00:00Z`.
- Неизвестные поля в теле запроса отклоняются.
- Пользователь и его компания определяются backend по сессии.

На backend нужно настроить `APP_ORIGIN` точно под адрес фронта, включая порт:

```dotenv
APP_ORIGIN=http://localhost:3000
```

Это настройка backend; её изменение нужно согласовать с бэкендером и применить
перезапуском Gateway. В браузере последовательно используйте один hostname,
например `localhost` для обоих приложений. Cookie имеют SameSite=Lax; схема с
разными сайтами требует отдельной настройки интеграции.

Во фронте можно задать:

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:8080/api/v1
```

## 2. Последовательность экранов

1. Пользователь заполняет анкету сотрудника и реквизиты компании.
2. Фронт может предварительно проверить название и ИНН через `/auth/company-check`.
3. Фронт отправляет `/auth/register`, получает `pending_email`.
4. Пользователь подтверждает почту через `/auth/verify-email`, получает `pending_approval`.
5. Пользователь входит через `/auth/login`; до одобрения видит экран ожидания.
6. Бэкендер подтверждает принадлежность сотрудника к компании служебной командой.
7. Фронт запрашивает `/auth/me`, получает `active` и открывает основной интерфейс.

Вход возможен и до подтверждения почты: экран выбирается по `access_status`.
Регистрация и подтверждение почты сами по себе не создают сессию. Если пользователь
ещё не вошёл, для `/auth/me` сначала нужен `/auth/login`.

| `user.access_status` | Экран | Доступ |
| --- | --- | --- |
| `pending_email` | Подтверждение почты | После входа доступны `/auth/me` и выход |
| `pending_approval` | Ожидание подтверждения компании | После входа доступны `/auth/me` и выход |
| `active` | Основной интерфейс | Данные своей компании и общедоступные материалы |
| `blocked` | Сообщение о блокировке | Вход запрещён, сессии отозваны |

Публичные методы регистрации, проверки компании и почты вызываются без сессии.
Должность — строковое поле профиля. Бизнес-ролей и выбора прав на фронте нет.

## 3. Быстрая таблица заголовков

| Запрос | JSON | `Idempotency-Key` | `X-CSRF-Token` |
| --- | --- | --- | --- |
| `POST /auth/company-check` | Да | — | — |
| `POST /auth/register` | Да | Обязателен | — |
| `POST /auth/verify-email` | Да | — | — |
| `POST /auth/resend-verification` | Да | — | — |
| `POST /auth/login` | Да | — | — |
| `GET /auth/me` | Тела нет | — | — |
| `POST /auth/logout` | Тело не требуется | — | Обязателен |
| `POST /news/submissions` | Да | Обязателен | Обязателен |

Cookie отправляет браузер при `credentials: "include"`. Заголовок `Origin` браузер
также выставляет самостоятельно. Пользовательский Bearer-токен для этого API не нужен.

## 4. Предварительная проверка компании

```http
POST /auth/company-check
Content-Type: application/json
```

Тело, схема `CompanyCheckInput`:

```json
{
  "inn": "9900000017",
  "name": "Тест Металл Альфа"
}
```

Успех: **200 OK**, схема `CompanyCheck`:

```json
{
  "company_id": "company-inn-9900000017",
  "inn": "9900000017",
  "canonical_name": "ООО «Тест Металл Альфа»",
  "status": "matched_mock",
  "provider": "mock-registry-v1",
  "checked_at": "2026-10-22T17:00:00Z"
}
```

Backend проверяет контрольную цифру ИНН и совпадение названия с мок-справочником.
Игнорирует регистр, лишние пробелы и варианты двойных кавычек. Допустимые сокращения
заданы явно. Предварительная проверка не создаёт компанию; при регистрации
реквизиты проверяются повторно.

Обработка: `400 invalid_inn` — исправить ИНН; `400 invalid_company_name` — исправить
название; `422 company_name_mismatch` — название не соответствует ИНН;
`422 company_not_found` — запись отсутствует в тестовом справочнике.
`matched_mock` отображается как тестовая проверка реквизитов и не означает
подтверждённую принадлежность сотрудника к организации.

## 5. Регистрация сотрудника

```http
POST /auth/register
Content-Type: application/json
Idempotency-Key: <UUID одной отправки анкеты>
```

Тело, схема `RegistrationInput`:

```json
{
  "full_name": "Иван Иванов",
  "job_title": "Финансовый директор",
  "email": "employee@example.test",
  "password": "Registration-Test-2026!",
  "company_name": "Тест Металл Альфа",
  "inn": "9900000017"
}
```

Все поля обязательны:

| Поле | Что передавать | Проверка backend |
| --- | --- | --- |
| `full_name` | ФИО одной строкой | 2–300 символов, без управляющих символов |
| `job_title` | Должность свободным текстом | 2–300 символов, без управляющих символов |
| `email` | Рабочая почта | Корректный email, до 254 символов |
| `password` | Введённый пароль | 12–72 байта UTF-8 |
| `company_name` | Название компании | 2–300 символов и совпадение со справочником |
| `inn` | ИНН компании строкой | 10 ASCII-цифр и верная контрольная цифра |

У ФИО, должности и названия удаляются пробелы по краям. Email дополнительно
приводится к нижнему регистру. Пароль передаётся без изменения и предварительного
хеширования. Для подсчёта байтов UTF-8 используйте `new TextEncoder().encode(password).length`.
В OpenAPI ограничения строки пароля дополнены описанием байтовой проверки;
для кириллицы проверяйте именно длину UTF-8.

В регистрации **не передавать** выручку, регион, отрасль, КПП, ОГРН, `company_id`,
роль, статус и признак подтверждения. Поле повторного пароля проверяется локально
и в запрос не включается.

Название в проверке компании называется **`name`**, в регистрации — **`company_name`**.

Успех: **201 Created**, схема `RegistrationResult`:

```json
{
  "user": {
    "id": "6b97f4493b10482f88228ae3f9d33909",
    "email": "employee@example.test",
    "company_id": "company-inn-9900000017",
    "full_name": "Иван Иванов",
    "job_title": "Финансовый директор",
    "email_verified": false,
    "access_status": "pending_email"
  },
  "company_check": {
    "company_id": "company-inn-9900000017",
    "inn": "9900000017",
    "canonical_name": "ООО «Тест Металл Альфа»",
    "status": "matched_mock",
    "provider": "mock-registry-v1",
    "checked_at": "2026-10-22T17:00:00Z"
  },
  "email_delivery": "mock"
}
```

Показать экран подтверждения почты. Примеры ID и времени условные: фронт использует
значения фактического ответа. Почтового токена и сессионных cookie в ответе регистрации нет.

### Повторная отправка

Генерировать `Idempotency-Key` через `crypto.randomUUID()` один раз на отправку анкеты.
При сетевом сбое сохранить этот ключ в состоянии формы и повторить тот же запрос.
Длина ключа — 8–128 символов.

- Те же email, ключ и нормализованное тело: **200**, прежний пользователь.
- Тот же email и ключ с изменённой анкетой: **409 idempotency_conflict**.
- Занятый email с другим ключом: **409 email_already_registered**.

Изменение анкеты требует нового ключа. Уже созданный аккаунт таким способом не
редактируется. Пароль не сохранять в localStorage и не включать в логи.

## 6. Подтверждение почты

```http
POST /auth/verify-email
Content-Type: application/json
```

Тело, схема `VerifyEmailInput`:

```json
{
  "token": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

Здесь показан формат: реальный токен нужно получить из мок-письма. Токен — строка
из 64 символов, одноразовый, действует 30 минут. Сейчас бэкендер получает его
служебной командой и передаёт для тестирования. Настоящей отправки писем нет.
Фронт не может получить токен через публичный API.

Успех: **200 OK**, схема `UserResponse`:

```json
{
  "user": {
    "id": "6b97f4493b10482f88228ae3f9d33909",
    "email": "employee@example.test",
    "company_id": "company-inn-9900000017",
    "full_name": "Иван Иванов",
    "job_title": "Финансовый директор",
    "email_verified": true,
    "access_status": "pending_approval"
  }
}
```

Показать ожидание подтверждения принадлежности к компании. Если сессии ещё нет,
предложить вход. При `400 invalid_or_expired_verification` предложить перевыпуск токена.

### Повторное письмо

```http
POST /auth/resend-verification
Content-Type: application/json
```

Тело, схема `ResendVerificationInput`:

```json
{
  "email": "employee@example.test"
}
```

Успех: **202 Accepted**, схема `ResendVerificationResult`:

```json
{
  "status": "accepted",
  "email_delivery": "mock"
}
```

Старый токен становится недействительным. Ответ одинаков для неизвестного email,
уже подтверждённого пользователя и действующей заявки: по этому ответу нельзя
определять наличие аккаунта.

## 7. Вход

```http
POST /auth/login
Content-Type: application/json
```

Тело, схема `LoginInput`:

```json
{
  "email": "employee@example.test",
  "password": "Registration-Test-2026!"
}
```

Успех: **200 OK**, схема `AuthResponse`:

```json
{
  "user": {
    "id": "6b97f4493b10482f88228ae3f9d33909",
    "email": "employee@example.test",
    "company_id": "company-inn-9900000017",
    "full_name": "Иван Иванов",
    "job_title": "Финансовый директор",
    "email_verified": true,
    "access_status": "active"
  },
  "csrf_token": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "expires_at": "2026-10-23T01:00:00Z"
}
```

Использовать фактический `csrf_token` из ответа. Пример выше показывает активного
пользователя; до подтверждения придёт соответствующий ожидающий статус.

Backend устанавливает HttpOnly-cookie `alfa_session` и `alfa_csrf`. JavaScript их
не читает; браузер сам отправляет cookie при `credentials: "include"`.
CSRF-токен берётся из JSON ответа и хранится в состоянии приложения.

Сессия действует максимум 8 часов, при бездействии 30 минут потребуется новый вход.
`expires_at` отражает абсолютный срок; окончательное решение о действительности
сессии принимает backend при каждом запросе.

## 8. Восстановление сессии и ожидание одобрения

```http
GET /auth/me
```

Тело не нужно. Ответ **200 OK** имеет схему `AuthResponse`, как при входе.
Вызывать при запуске приложения и перезагрузке страницы, чтобы восстановить
пользователя, актуальный статус и CSRF-токен.

- `200 active` — открыть основной интерфейс.
- `200 pending_email` — показать подтверждение почты.
- `200 pending_approval` — показать ожидание одобрения.
- `401` — показать вход.
- `503` — показать недоступность сервиса и возможность повторить.

На экране ожидания можно дать кнопку «Проверить статус». Обновление выполняется
через `/auth/me`; WebSocket и push-уведомления об одобрении не реализованы.
Одобрение выполняет бэкендер после проверки принадлежности сотрудника; публичного
метода одобрения для фронта нет. Самостоятельно выставить `active` нельзя.

## 9. Выход

```http
POST /auth/logout
X-CSRF-Token: <csrf_token из login или me>
```

Тело не требуется. Успех — **204 No Content**, без JSON. После ответа очистить
состояние пользователя и CSRF-токен, открыть экран входа. Не вызывать
`response.json()` для ответа 204.

## 10. Данные основного интерфейса

Все методы требуют действующей сессии и `access_status=active`.
Компания определяется по cookie, `company_id` в запрос отправлять не нужно.

| Метод | Назначение | Схема ответа |
| --- | --- | --- |
| `GET /companies/current` | Реквизиты и сведения о компании | `Company` |
| `GET /companies/current/profile` | Профиль показателей компании | `Profile` |
| `GET /news?limit=20&offset=0` | Публикации с коротким excerpt | `ArticlePage` |
| `GET /news/{id}` | Публикация с полным текстом | `Article` |
| `GET /events?limit=20&offset=0` | Кандидаты событий | `EventPage` |
| `GET /events/{id}` | Событие и ссылки на публикации | `Event` |
| `GET /analytics/summary` | Статистика обработки | `AnalyticsSummary` |

`limit` — от 1 до 100, по умолчанию 20; `offset` — от 0, по умолчанию 0.
Список возвращает `items`, `limit`, `offset`, `total`. Пустой список — нормальный ответ.

Пример пустого списка, схема `ArticlePage`:

```json
{
  "items": [],
  "limit": 20,
  "offset": 0,
  "total": 0
}
```

Компания сразу после регистрации, схема `Company`:

```json
{
  "id": "company-inn-9900000017",
  "name": "ООО «Тест Металл Альфа»",
  "inn": "9900000017",
  "okved": null,
  "sector": "",
  "region": "",
  "products": {},
  "ved": {}
}
```

Сведения для метрик подтягиваются отдельно. До обогащения `okved=null`, регион и
отрасль пустые, `revenue_minor` отсутствует. Запрос профиля вернёт 404, пока профиль
не загружен; показать «Профиль готовится / данных пока нет». Когда выручка появится,
`revenue_minor` будет выражена в копейках.

Текст новости получать через `/news/{id}`, в списке использовать `excerpt`.
`published_at` может быть null, ссылка может быть пустой у ручной загрузки.
Неизвестную дату показывать как «Дата не указана».

События сейчас могут иметь `status=awaiting_tagging`: это ожидание ML-разметки.
Готовые прогнозы и AI-выводы пока не предоставляются. Методы Insight/Ranking/Forecast
для фронта в текущем API не реализованы.

Запрос чужого `company_id` даёт 403. Чужой приватный объект по ID возвращает 404.

## 11. Ручное добавление публикации

```http
POST /news/submissions
Content-Type: application/json
X-CSRF-Token: <csrf_token>
Idempotency-Key: <UUID одной загрузки>
```

Вариант A — текст, схема `SubmissionInput`:

```json
{
  "title": "Ручная новость для анализа",
  "text": "Текст публикации, которую нужно обработать."
}
```

`title` обязателен для текста, максимум 500 символов. `text` — максимум 200000
символов. Необязательный `published_at` — строка с датой и часовым поясом.
Если дата неизвестна, поле нужно опустить.

Вариант B — зарегистрированная мок-ссылка, схема `SubmissionInput`:

```json
{
  "url": "https://html.test/articles/grain"
}
```

Отправлять либо текст, либо URL. Произвольные реальные сайты сейчас не принимаются.
Ссылка выше используется как ключ локальной фикстуры; фронту не нужно открывать её
для получения текста.

Успех: **202 Accepted**, схема `Submission`:

```json
{
  "id": "submission-example",
  "company_id": "company-inn-9900000017",
  "user_id": "6b97f4493b10482f88228ae3f9d33909",
  "status": "pending",
  "created_at": "2026-10-22T17:00:00Z"
}
```

202 означает приём задания, обработка асинхронная. Проверять состояние:

```http
GET /news/submissions/{id}
```

Схема ответа — `Submission`:

- `pending` / `retry` — обработка продолжается.
- `stored` — использовать `article_id` для запроса `/news/{article_id}`.
- `quarantined` / `failed` — показать ошибку обработки, в ответе может быть `error_code`.

Повтор с тем же ключом и содержимым вернёт то же задание; другое содержимое с
прежним ключом — 409. Ключ загрузки относится к текущему пользователю и компании.
Ручные загрузки доступны только сотрудникам своей компании.

## 12. Формат ошибок

Любая штатная ошибка содержит `code` и `request_id`, схема `Error`:

```json
{
  "code": "company_name_mismatch",
  "request_id": "8b50ec31edb74859b6a5ec91c71005a4"
}
```

`request_id` сохранять для диагностики, пользователю показывать понятный текст
по `code`. Для неизвестной ошибки использовать общее сообщение и возможность повторить.

| HTTP | `code` | Действие фронта |
| --- | --- | --- |
| 400 | `invalid_input` | Проверить JSON, типы и неизвестные поля |
| 400 | `invalid_registration` | Проверить обязательные поля и ограничения анкеты |
| 400 | `invalid_inn` | Подсветить ИНН |
| 400 | `invalid_company_name` | Подсветить название |
| 400 | `invalid_idempotency_key` | Исправить заголовок запроса |
| 400 | `invalid_or_expired_verification` | Предложить новый токен подтверждения |
| 400 | `invalid_pagination` | Исправить limit/offset |
| 400 | `provide_text_or_url` / `invalid_manual_text` | Исправить ручную загрузку |
| 400 | `unknown_mock_url` | Использовать зарегистрированную тестовую ссылку |
| 401 | `invalid_credentials` | Показать ошибку почты или пароля |
| 401 | `authentication_required` / `invalid_session` | Показать вход |
| 403 | `membership_not_active` | Показать этап подтверждения по `/auth/me` |
| 403 | `access_blocked` | Показать блокировку |
| 403 | `company_access_denied` | Закрыть доступ к чужой компании |
| 403 | `csrf_required` | Обновить CSRF через `/auth/me` |
| 403 | `origin_denied` | Проверить APP_ORIGIN с бэкендером |
| 404 | `not_found` | Показать отсутствие данных или недоступный объект |
| 409 | `email_already_registered` | Предложить вход |
| 409 | `idempotency_conflict` | Проверить ключ и тело регистрации |
| 409 | `conflict` | Проверить ключ ручной загрузки и содержимое |
| 415 | `json_required` | Исправить Content-Type |
| 422 | `company_name_mismatch` | Название не соответствует ИНН |
| 422 | `company_not_found` | Компания отсутствует в мок-справочнике |
| 429 | `too_many_attempts` | Выдержать время из Retry-After |
| 503 | `registration_unavailable` / `authentication_unavailable` / `upstream_unavailable` | Показать временный сбой |
| 504 | `upstream_timeout` | Показать превышение времени ожидания |

Не направлять пользователя на повторный вход при каждом 403 или 503:
ожидание одобрения и временный сбой имеют отдельные состояния интерфейса.
При повторе изменяющих запросов учитывать Idempotency-Key.

Ограничения: регистрация — 10 запросов/мин на IP и 3 на email; проверка компании —
20/мин на IP; проверка токена — 20/мин на IP; перевыпуск — 10/мин на IP и 3 на email;
вход — 20/мин на IP и 10 на email. При 429 приходит `Retry-After: 60`.

## 13. Пример fetch для регистрации

```ts
const API_BASE = process.env.NEXT_PUBLIC_API_BASE_URL
  ?? "http://localhost:8080/api/v1";

// Создать один раз при отправке анкеты, сохранить для сетевых повторов.
const registrationKey = crypto.randomUUID();

const payload = {
  full_name: fullName,
  job_title: jobTitle,
  email,
  password,
  company_name: companyName,
  inn,
};

const response = await fetch(`${API_BASE}/auth/register`, {
  method: "POST",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": registrationKey,
  },
  body: JSON.stringify(payload),
});

const result = await response.json();

if (!response.ok) {
  // Показать сообщение по result.code; request_id сохранить для диагностики.
} else {
  // Сохранить user в состоянии и показать подтверждение почты.
  // Успешными являются и 201, и 200 при повторе.
}
```

Для защищённого POST добавить `X-CSRF-Token` из `/auth/login` или `/auth/me`.
Для GET тело не передавать. Для ответа 204 не выполнять JSON-парсинг.

## 14. Тестовые данные и что уточнить у бэкендера

Компании для новой регистрации:

| ИНН | Название для отправки |
| --- | --- |
| `9900000017` | `Тест Металл Альфа` |
| `9900000024` | `Тест Строй Альфа` |
| `9900000031` | `Тест Импорт Альфа` |
| `9900000049` | `Тест Агро Альфа` |

Это синтетические записи локального справочника. Их наличие в настоящем реестре
не проверялось. Для каждой новой регистрации использовать уникальный тестовый email.

Существующие активные демо-учётки: `metal@example.test`, `metal2@example.test`,
`build@example.test`, `import@example.test`, `agro@example.test`. Пароль по умолчанию
`DemoOnly-2026!`; если он изменён в окружении backend, актуальное значение даст бэкендер.

Для тестирования нужно получить от бэкендера:

1. Доступный адрес API и подтверждение настройки APP_ORIGIN под фронт.
2. Мок-токен после регистрации или перевыпуска.
3. Одобрение принадлежности к компании после подтверждения почты.

Бэкендер получает письмо командой `api-gateway /app mock-email --email EMAIL`
в контейнере, подтверждает заявку `approve-registration --user-id USER_ID --operator OPERATOR`.
Фронт не вызывает эти команды и не получает прямой доступ к БД.

Мок-регистрация в режиме APP_ENV=production выключена и возвращает 503.
Фактическая отправка писем, реальные реестры компаний, новостные сайты и ML
в текущем контуре не подключены. Поля AI-выводов и прогнозов пока не следует
считать доступными через API.

Полный контракт: [OpenAPI](../../contracts/openapi/backend.yaml).
Готовое тело регистрации: [registration.json](examples/registration.json).
Описание процесса для backend: [registration.md](../architecture/registration.md).
