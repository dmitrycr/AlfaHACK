# Реальные LLM: проверка 23 октября 2026

Проверка разрешена пользователем. Использован ключ из локального .env; его
значение не включалось в запросы модели, Git, диагностические отчёты или вывод.
Только официальные основной и резервный адреса, проверка TLS, без редиректов.
Данные компаний и новости синтетические; реальные СМИ, frontend, ML и RAG не
подключались. Картинки и VL-модель не проверялись по согласованному ограничению.

## Объём и результат

Выполнены чтение бюджета/метаданных и 12 ограниченных генеративных запросов.
Для пяти штатных операций использованы настоящие промпты, OutputSchema,
маршрутизация и ValidateInput/ValidateOutput проекта. Это прямые HTTP-пробы,
а не успешный сквозной запуск production-адаптера/очереди/оркестратора в HTTP mode.
Такой запуск пока блокируется несовместимостью бюджетного контракта и другими
перечисленными ниже проблемами. Изменения продуктового кода в рамках проверки
не вносились; фоновые платежи не включались.

## Критические несовместимости

### P1: бюджетный endpoint не совпадает с адаптером

Подтверждённый URL: https://changellenge.up.railway.app/key/info, также работает
резервный хост. Данные находятся в info: max_budget, spend, budget_reset_at.
Готового числового remaining нет. Адаптер сейчас умеет один JSON Pointer к
готовому остатку, поэтому не может корректно получить max_budget минус spend.
Указывать max_budget как remaining нельзя: это проигнорирует уже потраченное.
Нужны явный режим вычисления остатка, строгие decimal-проверки, период и тесты
на реальную обезличенную форму ответа. Сырой key/info сохранять и логировать нельзя.

### P1: текущие цены не соответствуют фактическому учёту

Фактический usage.cost совпадает с x-litellm-response-cost. В первом GLM-вызове
35 входных и 38 выходных токенов: cost=0.00281322952625. Расчёт по значениям PDF
при допущении «за миллион» даёт 0.0008245, разница примерно в 3.412 раза.
Такое же отношение получилось для двух других GLM-вызовов. Для DeepSeek и Gemma
отношения другие (примерно 2.977 и 1.568). Подменять тариф единым множителем нельзя.
Официальная текущая цена/единица не подтверждена; model/info не вернул цены.
Нужно отделить фактическую стоимость шлюза от оценки по тарифу, подтвердить
валюту/единицу и корректный резерв. Локальный журнал пока не является точным биллингом.

spend обновляется с задержкой: немедленный GET после ответа может показать старое
значение. Поэтому только чтения баланса без локального учёта новых обязательств
недостаточно. Уже реализованную защиту от параллельных расходов следует сохранить.

### P1: семантические требования отсутствуют в контракте модели

GLM вернул непустой reason при status=ready, хотя валидатор требует пустую строку.
Вернул ОКВЭД 64.11 и 64.19, хотя приложение принимает только двухзначный класс.
Схема/промпт не доводят эти ограничения достаточно явно до модели. Ответ корректен
как JSON, но отвергается после оплаченного вызова. Нужны согласованные JSON Schema,
промпт, примеры и runtime validation, включая условные ограничения.

### P1: Gemma не соблюдает формат ответа проверяющего агента

Два разных входа дали Markdown fences и дополнительное поле $ref. Strict JSON
закономерно отклоняет оба ответа. На ложном утверждении сама оценка была верной,
но рабочая цепочка всё равно не сможет опубликовать карточку. Нужны инструкции
о различии схемы и экземпляра, минимальный пример результата, проверка возможностей
structured output и ограниченная явно описанная нормализация либо смена маршрута.
Просто отключать строгую проверку недопустимо.

### P1: таймауты не соответствуют реальным задержкам

Текущий конфигурационный default 3 секунды недостаточен для тегирования, профиля
и чата на этих примерах. Даже максимальные 30 секунд не дали результата карточки
Qwen. Нельзя считать такой исход бесплатным отказом: результат/списание неизвестны.
Нужны согласованные таймауты HTTP, RPC, оркестратора, задания и lease; проверка
управления reasoning/latency и сценария позднего результата. Слепой повтор запрещён.

### P1: reasoning съедает выходной лимит

На тесте недоверенной инструкции GLM потратил 1861 из 2000 completion на reasoning;
итоговый JSON оборвался. finish_reason=length корректно блокирует результат.
Нужны проверенные настройки reasoning для каждой модели и запас выходного лимита,
измеренный на реальных схемах. Поддержка параметров reasoning пока не проверялась;
угаданные параметры в продуктивные запросы не добавлялись.

## Что подтвердилось

- max_tokens принимается и ограничивает выход на проверенных запросах.
- model в сохранённых ответах совпадает с запрошенным идентификатором.
- usage есть в сохранённых успешных ответах, reasoning не нужно прибавлять
  второй раз к completion_tokens.
- DeepSeek-профиль и GLM-чат проходят действующие валидаторы на этих примерах.
- Чат сообщает об отсутствии неизвестных числовых/регистрационных данных.
- Проверяющая модель обнаружила внедрённые ложные утверждения.
- Оба официальных адреса доступны; реальная генерация через резервный адрес работает.
- Строгая проверка не пропускает неподходящие ответы. Это защита, но пока также
  причина отказов полезных результатов из-за несовпадения контрактов.

## Расход и состояние после проверки

Первый spend=2.122475845284601, последний=3.021880880641351 при max_budget=500.
Наблюдаемое увеличение около 0.90 единицы бюджета; остаток около 496.98.
По инструкции бюджет выражен в рублях. Это общий счёт команды, поэтому разницу
нельзя строго приписать только этим тестам. Возможны задержки обновления и
списания за запросы без полученного результата. Сброс: 2026-10-24T00:00:00Z.

Локальный AI после проверки: mode=mock, key_configured=true,
payment_gate_open=false. .env с правами 0600, ключ не добавлен в Git. Реальная
фоновая обработка, Kimi-route и внешний egress overlay не включались.

## План исправлений до реального E2E

1. Адаптировать бюджет и фактический учёт стоимости, не ослабляя ограничения.
2. Согласовать схему, промпты и runtime-ограничения; версии промптов обновить,
   чтобы старый кеш не скрывал результаты проверки.
3. Исправить формат проверяющего агента и протестировать отрицательные случаи.
4. Определить настройки reasoning/лимитов и пересчитать всю цепочку таймаутов.
5. После локальных regression/race-тестов выполнить небольшой реальный E2E:
   новость → профиль → карточка → проверка → чат, с журналом расходов, кешем,
   рестартом и запретом повторных платежей после uncertain.

Перечисленное — план дальнейших изменений, а не уже выполненные исправления.
Успешный предыдущий mock E2E не заменяет этот реальный E2E.
