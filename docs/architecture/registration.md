# Регистрация сотрудника и проверка компании

Регистрация принимает ФИО, должность, рабочую почту, пароль, название компании и
ИНН. Выручка, регион, отрасль, КПП и ОГРН не запрашиваются. Неизвестные поля
отклоняются. Должность — данные профиля сотрудника, бизнес-ролей нет.

## Границы сервисов

API Gateway хранит учётные записи, хеши паролей bcrypt, сессии, состояния доступа,
заявки, подтверждения почты и журнал решений оператора в схеме auth.
Company Service хранит реквизиты, уникальную привязку ИНН к компании и источник
проверки в схеме company. Чужие схемы не читаются, взаимодействие идёт по gRPC.

CompanyRegistry.Lookup — интерфейс для будущего внешнего адаптера. Сейчас
реализован только MockRegistry с четырьмя локальными записями. Он не обращается
в сеть и не подтверждает существование юридического лица. Результат помечается
status=matched_mock, provider=mock-registry-v1 и временем проверки.
Чтобы подключить настоящий провайдер, нужно реализовать адаптер, сопоставление
его свидетельств и статусов и включить отдельный режим конфигурации. Регистрационная
анкета и привязка сотрудника от этого не меняются.

## Проверка реквизитов

MVP поддерживает ИНН юридических лиц: 10 ASCII-цифр с проверкой контрольной цифры;
нулевой ИНН отклоняется. Формат ИНН описан [ФНС](https://www.nalog.gov.ru/rn77/terms/7756931/).
Корректная контрольная цифра не подтверждает существование компании.

Компания ищется по ИНН. Название сравнивается с каноническим и явно заданными
алиасами: игнорируются регистр, повторные пробелы и варианты двойных кавычек.
Нечёткое сравнение, исправление опечаток и произвольное удаление правовой формы
не выполняются. Ошибка контрольной цифры — 400 invalid_inn, несовпадение названия —
422 company_name_mismatch, отсутствие в мок-справочнике — 422 company_not_found.
Недоступность зависимости — 503 registration_unavailable, а не успешная проверка.

Фикстуры полностью синтетические; номера подобраны для тестов контрольной цифры,
наличие таких ИНН в реестрах не проверялось. Это отдельные компании, а не привязка
реальных организаций к обезличенным компаниям датасета.

| ИНН | Название | Допустимый короткий вариант |
| --- | --- | --- |
| 9900000017 | ООО «Тест Металл Альфа» | Тест Металл Альфа |
| 9900000024 | ООО «Тест Строй Альфа» | Тест Строй Альфа |

## Состояния пользователя

1. POST /auth/register проверяет анкету и реквизиты, обеспечивает запись компании
   и создаёт пользователя со статусом pending_email. Ответ не содержит токен почты.
2. POST /auth/verify-email принимает одноразовый токен со сроком 30 минут.
   После проверки состояние меняется на pending_approval.
3. Оператор независимо подтверждает принадлежность сотрудника к организации
   и выполняет approve-registration. Состояние становится active.
4. revoke-access устанавливает blocked, удаляет сессии и незавершённые подтверждения.

Вход разрешён в pending_email и pending_approval, но доступны только auth/me и
выход; все бизнес-методы возвращают 403 membership_not_active. Статус читается
из БД при каждом запросе, поэтому активная сессия увидит подтверждение оператора.
Заблокированный пользователь не может войти. Проверка почты и правильный ИНН
никогда сами по себе не открывают доступ к компании.

## Мок-почта и операторские команды

Настоящей отправки писем нет. Мок-сообщение хранится в auth.mock_mail. Подтверждение
или отзыв доступа удаляет его, перевыпуск заменяет; просроченные сообщения не выдаются командой.
Верификационный токен хранится хешированным в auth.email_verifications;
исходное значение присутствует только в тестовом почтовом ящике. Это намеренная
особенность мок-доставки. Она доступна оператору с учётными данными схемы auth.
В публичных ответах и логах токен не печатается. Команда mock-email выводит его
по явному запросу локального оператора. В production регистрация с моками выключена;
mock-email запрещена, а чтение уже существующих данных работает как прежде.

После регистрации получить тестовое письмо:

```sh
docker compose --env-file .env -f infrastructure/docker/compose.yaml exec -T \
  api-gateway /app mock-email --email employee@example.test
```

Передать token из вывода в POST /api/v1/auth/verify-email. Затем, после проверки
принадлежности сотрудника, подтвердить заявку по user.id из ответа регистрации:

```sh
docker compose --env-file .env -f infrastructure/docker/compose.yaml exec -T \
  api-gateway /app approve-registration --user-id USER_ID --operator local-operator
```

Для отзыва используется revoke-access с теми же аргументами. Решения и имя
оператора сохраняются в auth.membership_decisions. Отдельных бизнес-ролей и
публичного метода подтверждения нет. Идентификатор оператора задаётся им самим;
пока это журнал локальных действий, а не подтверждённая внешняя идентичность.

POST /auth/resend-verification перевыпускает токен, старый становится недействительным.
Ответ 202 одинаков для неизвестного email и пользователя, которому письмо не требуется.

## Повторы, сбои и миграции

Регистрация требует Idempotency-Key длиной 8–128. Ключ действует в рамках email.
Повтор того же запроса возвращает того же пользователя (200 вместо 201), изменение
анкеты с прежним ключом даёт 409. Отпечаток включает HMAC от нормализованной анкеты,
пароль в исходном виде не сохраняется. Другой ключ для уже занятого email даёт 409.
INTERNAL_KEY должен сохраняться между перезапусками; его ротация меняет отпечатки
повторяемых запросов и требует отдельной процедуры.

У компании уникальный ИНН. Повторный запрос не перезаписывает данные обогащения.
Создание компании идемпотентно, запись пользователя, запроса и письма атомарна
в auth. Межсервисной транзакции нет: если auth недоступен после создания компании,
остаётся карточка без сотрудников и прав; повтор завершит регистрацию. Удалять
такую компанию автоматически нельзя — параллельно к ней мог обратиться другой
сотрудник. Бизнес-доступ определяется состоянием пользователя в auth.

Данные для метрик остаются незаполненными до отдельного обогащения.
ОКВЭД возвращается как null, регион/отрасль — как пустые строки, выручка отсутствует.
Аналитический профиль при регистрации не выдумывается: /companies/current/profile возвращает
404, пока профиль не загружен. Порог выручки при регистрации не проверяется.

Миграции 002 добавляются поверх неизменённых 001. Старые пользователи и сессии
сохраняются; существующим учёткам присваиваются email_verified=true и active.
Новые пользователи создаются явно с pending_email и email_verified=false.
Регистрация ограничена 10 запросами/мин на IP и 3 на email; проверка компании —
20/мин на IP, проверка токена — 20/мин, перевыпуск — 10/мин на IP и 3 на email.
Это отдельные счётчики от ограничений входа. Регистрационные POST требуют JSON
и разрешённый Origin, если браузер передал этот заголовок.
