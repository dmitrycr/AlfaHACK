# LLM на стороне бэка: мок-контур v1

Это описание первой версии. Актуальный оркестратор, HTTP-провайдер и ограничения
платных вызовов описаны в [llm-orchestrator.md](llm-orchestrator.md).

Реализованы три пути: публикация → подготовленное событие; Match + профиль +
событие → проверенная карточка; карточка → чат. Реальных LLM-вызовов, сетевого
поиска и изменений frontend/ML нет. Исполняются семь Go-сервисов из исходной
архитектуры; `ai-agent-service` и `insight-service` больше не пустые.

`ai-agent-service` владеет схемой `agent`: вызовы, кеш, симуляционный бюджет,
диалоги и задания чата. `insight-service` владеет `insights`: Match и задания
карточек. `event-service` владеет событиями, подготовленными версиями и заданиями
разбора в `events`. Сервисы не читают таблицы друг друга; обмен — через gRPC
и Kafka. Общие пакеты содержат только контракты и повторно используемые адаптеры.

## Задания и версии

Создание кандидата и задания разбора выполняется одной транзакцией. Воркер
читает конкретные ревизии статей из News Service, затем вызывает AI Service вне
транзакции. Сохраняет ответ только для исходной версии события, атомарно с
`event.tagged` в outbox. События без источников с датой — `insufficient_data`,
непрофильные — `noise`. Изменение публикации сбрасывает старую готовность.
API отдаёт только подготовленные данные текущей версии.

`pending → running → ready`; при сбое `retry`, максимум три попытки; затем
`failed`. Обновлённый вход даёт `obsolete`. Лизинг задания — 60 секунд,
выполнение ограничено 20 секундами, записи защищены токеном лизинга.
После падения процесса просроченное задание подхватывает другой воркер;
просроченная третья попытка становится `failed`. Reconcile событий раз в 10 секунд
отражает окончательный сбой в `tagging_failed`, сохраняя ревизию и outbox.

Исторические `awaiting_tagging`-кандидаты получают задания через backfill.
Существующая миграция `001_events` не изменена; новые таблицы находятся в `002`.
Схемы `agent` и `insights` создаются до старта их владельцев.

Карточка закрепляет Company/Profile, PreparedEvent, Match, признаки и найденные
фрагменты. Версии проверяются перед генерацией и после проверки. Между разными
сервисами нет общей транзакции: карточка содержит явные версии и может стать
исторической сразу после публикации. Она автоматически не переписывается.

## Провайдер, проверка, кеш и бюджет

Поддерживается только `LLM_MODE=mock`; другое значение завершает старт с ошибкой.
Мок детерминирован, не исполняет входные инструкции и не обращается в сеть.
`LLM_MOCK_SCENARIO`: `success`, `invalid_json`, `timeout`, `rate_limit`,
`unavailable`. Сценарий — конфигурация запуска, не пользовательский параметр.

Промпты встроены из `libs/go/llm/prompts`, версии — `*-backend-v1`.
Ключ кеша учитывает задачу, полный нормализованный вход, область доступа,
версию провайдера/контракта/справочника, версию и содержимое промпта.
Ошибочные ответы не кешируются. Для карточки выполняются две операции:
генерация и отдельная проверка. У обеих есть отдельные run ID.

Строгий JSON, справочники, диапазоны, версии и ссылки проверяются программно.
Источники/признаки могут ссылаться только на входной контекст. Программная
проверка ссылок не доказывает истинность утверждений; мок-проверка не заменяет
оценку качества будущей реальной модели. Результаты помечены `synthetic=true`.

Учёт в копейках: резерв 5 на вызов, симуляционная стоимость 1; токены оценочные.
Дневной лимит по UTC — 50000, параллельных вызовов — 4. Резерв и ограничение
параллелизма защищены общей короткой транзакцией. Попадания в кеш не расходуют
бюджет. Некорректный оплаченный ответ отражается в журнале, даже при отмене RPC.
Для реального провайдера ещё нужны адаптер, тарифы, фактический usage,
согласование недостоверного результата вызова при сетевом сбое и исходящая сеть.

Поиск аналитики выполняет `Knowledge`-адаптер. Сейчас `MockKnowledge` возвращает
синтетический фрагмент только для примера со ставкой; иначе — пустой результат.
Код будущего knowledge-service не менялся. Мок Match отделён от внешнего импорта.

## Запуск и проверки

Новый проект: `./scripts/setup.sh`, затем `make up`.
Существующий `.env`: `./scripts/setup-llm.sh` добавляет только недостающие значения.
При существующем PostgreSQL volume сначала выполнить
`./scripts/setup-llm.sh --database` при запущенном postgres, затем `make up`.
Скрипт не удаляет данные и не меняет пароли существующих ролей.

`make check` — vet, тесты, форматирование. `TEST_DATABASE_URL` должен указывать
на отдельный локальный PostgreSQL admin для создания временных тестовых баз.
`make native-e2e` поднимает семь реальных процессов и Kafka wire mock,
проверяет регистрацию, новости, LLM-события, карточку, чат, идемпотентность и
изоляцию компаний. `make contracts` требует jsonschema==4.25.1.

Схема генерируется `go run ./libs/go/cmd/llm-contracts`, примеры —
`go run ./libs/go/cmd/llm-examples`. Runtime-проверки межобъектных инвариантов
дополняют JSON Schema. Подключение реального ML и LLM — следующие интеграции.

API: [для фронта](../api/LLM_FRONTEND.md), [для ML](../api/LLM_ML_INTEGRATION.md).
