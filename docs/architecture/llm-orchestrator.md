# Оркестратор агентов и HTTP-провайдер v2

Собственная управляющая логика Go находится в `libs/go/llm/orchestrator.go` и
исполняется `ai-agent-service`. Агентные фреймворки не используются. Frontend и
ML не изменялись. Поддерживается только текст; модель VL не проходит allowlist.
RAG остаётся отдельной интеграцией; текущий Knowledge-адаптер синтетический.

## Маршруты

| Операция | Шаги | Модели по умолчанию |
|---|---|---|
| Новость | Программные правила → разбор | GLM |
| Профиль | Интерпретация агрегатов Company/Profile | DeepSeek |
| Карточка | Профиль → интерпретация → проверка | DeepSeek → Qwen 3.6 → Gemma |
| Чат | Ответ по закреплённой карточке и контексту | GLM |

Профиль строится автоматически по одинаковым правилам для всех компаний.
`FeaturesFor` использует поля компании, каналы и основания профиля и продукты.
Числа не генерируются LLM. Наблюдения и гипотезы профиля разделены и ссылаются на
ID признаков. Результат кешируется по снимку профиля, независимо от новости.

Точные идентификаторы: `z-ai/glm-5.3-flash`, `deepseek/deepseek-v4.1-flash`,
`qwen/qwen3.6-35b-a3b`, `google/gemma-4-26b-a4b-it`.
Kimi (`moonshotai/kimi-k2.6`) включается только через `LLM_ALLOW_KIMI=true`, для
важности события 5 и score >= 0.85; не больше двух реальных попыток в сутки.
Это технические пороги маршрутизации, не результат калибровки релевантности.
Назначить Kimi обычным массовым агентом конфигурация не разрешает.

## Состояние и повторная обработка

`agent.workflows` сохраняет состояние, область доступа, entity_id, номер попытки
и lease. `agent.steps` сохраняет подтверждённые результаты и ссылки на вызовы.
Перезапуск продолжает незавершённые шаги; завершённые модели повторно не вызываются.
Проверка, вернувшая `passed=false`, завершает обработку без публикации карточки.
Автоматического бесконечного исправления текста нет.

Журнал вызовов: `agent.calls`, кеш: `agent.cache`. Бизнес-карточками по-прежнему
владеет Insight Service, событиями — Event Service, диалогами — AI Service.
Остальные сервисы не читают таблицы агента напрямую.

Задание имеет lease 180 секунд и общий deadline 120 секунд; оркестратор — 100
секунд и lease 150 секунд; generation RPC — 110 секунд. Отдельный HTTP-вызов
ограничен 30 секундами, чтение бюджета — максимум 3 секундами. Это верхние пределы;
отмена внешнего контекста сокращает время. По умолчанию `LLM_TIMEOUT_SECONDS=3`
сохраняет быстрый мок-режим; реальный таймаут выбирается после проверки API.

## HTTP-протокол

Основной base URL: `https://changellenge.up.railway.app/v1`, резервный:
`https://api.alfahack-gateway26.ru/v1`. POST идёт в `/chat/completions`, ключ —
только в `Authorization: Bearer`. Тело: `model`, два текстовых `messages` и
подтверждённый параметр выходного лимита. Системное сообщение содержит промпт и
схему ответа; пользовательское — структурированный контекст как JSON.

Не отправляются неподтверждённые `response_format`, tools, streaming или параметры
управления рассуждениями. Ответы с tool calls/незавершённым выводом не исполняются.
Ожидается одна choice, `finish_reason=stop`, текстовый JSON и числовой usage.
Поддержка этих полей пока проверена на локальном HTTP-сервере, не на шлюзе.

TLS проверяется, прокси из окружения не подхватываются, редиректы запрещены.
Адреса ограничены двумя заданными хостами, размеры и соединения ограничены.
Ключи не входят в промпты, URL, кеш, ошибки, журнал или диагностический вывод.
Сканер проверяет также декодированные строки, чтобы JSON unicode-экранирование
не пропустило отражённый ключ в сохранённый результат. Это защита известного
секрета процесса, не универсальный поиск всех возможных секретов в данных.

## Ошибки и расход

При сбое до отправки заголовков POST можно перейти на резервный адрес. После
отправки таймаут, обрыв, 5xx, слишком большой ответ или неизвестный usage дают
`uncertain`. Автоматического повторного POST нет. Сохраняется консервативный резерв;
одинаковый вызов блокируется даже после перезапуска и смены транспортных настроек.
Такой исход требует сверки с провайдером; автоматическая сверка не реализована.

429 допускает ограниченную повторную попытку с `Retry-After` (до 5 минут), причём
предыдущий запрос без usage консервативно учитывается по резерву. HTTP 400/401/403/
404/422 останавливают цепочку и новые платежи текущей конфигурации. Ошибка бюджета
также останавливает платежи. Известные ошибки и политика повтора передаются через
gRPC ErrorInfo, чтобы очередь не создавала второй независимый цикл повторов.

Состояния задания/оркестратора: `pending`, `running`, `retry`, `ready`, `failed`,
а также `uncertain` для неопределённого оплачиваемого исхода. Устаревшие задания
бизнес-сервисов имеют `obsolete`. Нельзя автоматически отправлять то же сообщение
с новым ключом при `uncertain`. Смена модели/входа — новый запрос, который может
быть оплачен отдельно; менять их ради обхода неопределённого результата нельзя.

Денежный учёт в целых нанорублях, расчёт через rational arithmetic; `cost_minor`
оставлен для совместимости и округляется вверх. `cost_estimated=true` означает
резерв/неподтверждённый расход, а не известное списание. Даже при false это расчёт
по usage и настроенным тарифам; фактические списания подтверждает шлюз. В моках расходы явно
синтетические. Reasoning-токены не прибавляются второй раз к completion_tokens;
в реальном режиме нужно подтвердить, что completion_tokens уже их включает.

Перед каждым некешированным платным шагом читается `/key/info`. Полный URL
и JSON Pointer поля остатка задаются явно: документ не содержит схему ответа.
Локальный лимит <=500 рублей в сутки защищается транзакцией, дополнительно
вычитаются резервы и расходы, возникшие во время чтения остатка. Шлюз остаётся
единственным источником общего расхода других участников команды.
Сброс периода — 00:00 UTC / 03:00 МСК.

## Конфигурация без ключа

`./scripts/setup-llm.sh` добавляет только отсутствующие настройки в локальный
`.env`; существующие значения и секреты сохраняются. Ключ по умолчанию пустой.
`.env` исключён из Git и Docker context. Ключ нужен только AI Service, не фронту.

```sh
go run ./services/ai-agent-service/cmd/app check-llm-config
```

Команда не обращается к API и БД и выводит только наличие ключа, модели и
состояние конфигурационных блокировок. `payment_gate_open` не доказывает живую
совместимость API, а лишь отражает заданные настройки.

По умолчанию: `LLM_MODE=mock`, `LLM_PAID_CALLS_ENABLED=false`, единица тарифа 0,
все подтверждения false. Для HTTP нужны отдельные подтверждения:

- `LLM_PRICE_UNIT_TOKENS=1000` или `1000000`, `LLM_TARIFFS_CONFIRMED=true`;
- точные тарифы в `LLM_PRICES_JSON` (значения `input_rub` и `output_rub` строками);
- `LLM_KEY_INFO_URL`, `LLM_KEY_INFO_REMAINING_PATH`, `LLM_BUDGET_CONTRACT_CONFIRMED`;
- `LLM_TOKEN_LIMIT_PARAMETER` (`max_tokens` или `max_completion_tokens`) и подтверждение;
- `LLM_USAGE_CONTRACT_CONFIRMED`, ключ и отдельное разрешение платных вызовов.

Значения цен по умолчанию — ориентиры из предоставленного PDF, единица там
не подтверждена. Они не считаются действующим тарифом и не открывают платежи.
Формат ответа бюджета и лимитирующие параметры нужно подтвердить до включения.
После исправления ошибки конфигурации можно повысить `LLM_CONFIG_REVISION`;
неопределённый вызов этим не разблокируется. Все реплики используют одну версию.

Сеть backend остаётся внутренней. Шлюз дополнительно подключён к gateway-access,
чтобы Docker публиковал 127.0.0.1:8080 на хосте. AI и остальные прикладные сервисы
к этой сети не подключаются. Будущий HTTP-режим требует явного
overlay `infrastructure/docker/compose.llm-http.yaml`, который даёт исходящий
доступ только AI Service. Overlay сам по себе не открывает платные вызовы.

## Предварительная подготовка профилей

Для уже импортированных в Company Service компаний:

```sh
docker compose --env-file .env -f infrastructure/docker/compose.yaml exec ai-agent-service \
  /app prepare-profiles company-metal company-build
```

Команда ставит сохраняемые задания; выполняет их работающий AI Service.
Внутренние RPC: `AIService.QueueProfile` и `GetProfileJob`, только для сервисных
субъектов `ml-service`, `company-service`, `insight-service` с конкретной компанией.
Вход — company_id из подписанного контекста; сами факты читаются из Company Service.
Повтор с теми же данными переиспользует результат. Автоматического обхода всего CSV
в AI Service нет: CSV импортируется существующим контуром, затем передаются его ID.

## Наблюдаемость и проверки

В карточке появляются `workflow_id`, `profile_run_id`, `business_profile`.
`GET /api/v1/ai/workflows/{id}` показывает шаги, модели, статусы и run ID без
текстов контекста. Диалог возвращает workflow_id в результате сообщения.
Чужая компания не может получить журнал приватного сценария.

Проверки: `make check`, race-тесты LLM/очередей/AI/Insight/Event, схемы и Native E2E.
Ресурсные тесты выполняют 1000 запросов через инструментированный transport и
405 запросов через настоящий локальный HTTP transport, включая отмену и конкуренцию.
Проверяются тела ответов, HeapAlloc после GC и goroutine. Успешный прогон означает
отсутствие обнаруженного роста в этих сценариях; это не доказательство отсутствия
всех возможных утечек. Результаты конкретного прогона — в deployment/verification.md.


Для воспроизводимого длительного локального прогона: `make llm-soak` (по умолчанию
30 секунд, `LLM_SOAK_SECONDS=10..60`). Он использует только локальный HTTP-сервер
и тестовый секрет, не читает настоящий ключ из окружения. Диагностика без запросов
и без БД: `make llm-config`.

Внешний ML должен отправлять Match для уже отобранных событий. Нулевая оценка
блокирует генерацию до вызова агентов (`event_not_selected`); отбор top-N и
калибровка порогов остаются обязанностью ранжирования. После сброса дневного
бюджета возможен новый workflow с новым ключом задания; uncertain тем же
запросом не обходится ни новым днём, ни сменой транспортной конфигурации.
